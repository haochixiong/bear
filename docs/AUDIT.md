## 已修复

### 会误导修图的问题（最重要）

| 问题 | 修复 |
|---|---|
| 颜色分级建议用的是目标色调的**绝对值**，不是“目标 − 当前”。例如阴影已经偏黄，还建议继续加黄 | 风格模板和仿色都改为按差值换算；有回归测试 |
| ACR 预设导出拿不到混色器和颜色分级数值（整图和仿色模式的建议在结论里，没被收集），导出几乎是空的 | 从结论、风格结果、仿色曲线一起收集并去重 |
| 非肤色的“参考对比”给出的是肤色建议（只在红色 / 黄色范围里找，还写着“只作用于皮肤”） | 按区域本身的色相从六个 PS 范围里选；措辞和 ACR 通道也随之改变 |
| 肤色提亮可能被做两次：通道曲线已含明度，又单独给了一条复合曲线 | 有明度差时，通道曲线只改颜色，明度另用复合曲线 |
| 自动生成的图层直接把 Lab 色相度数当成 PS（HSB）滑块值（绿色约差 2 倍，肤色约差一半）；肤色用“黄色”范围，皮肤只落在它的边缘 | 先换算到 HSB；色相/饱和度范围以问题色为中心 |
| 半透明图层的透明部分被当成灰色参与统计（例如 6:3:1 里多出 22% 的“灰”） | 脏色和肤色分析用不透明蒙版；整体统计用本图层的不透明像素重采样填充 |
| “色相杂乱”的建议是“降低‘肤色’的饱和度”（ACR 没有这个通道） | 改为把两侧相邻通道的色相往主色收拢 |
| 肤色倾向在 0° 附近跳变；偏青的皮肤被说成“偏洋红”；“偏绿”可能给出负的度数 | 色相改为连续计算；增加“偏青/偏蓝”；度数不为负 |
| 浅肤色（日系、韩系、cos 的 C*/L* 约 0.14–0.22）在“自然通用”下被判为发灰 | 没选具体风格时，按明度参考所有内置风格的饱和度范围 |
| RAW 用 LibRaw 默认的 BT.709 曲线解码，中灰约暗 13 级 | 改用 sRGB 曲线 |
| 自定义肤色风格的色相区间跨过 0° 时判断错误；仿色曲线可能有重复输入点；取样大小标签没反映上限裁切 | 均已修正 |

### 桌面版

- 在其他模式下切换“风格”，会把已有的肤色结果替换掉。
- 仿色的参考作品一旦选过就换不掉，清空历史后仍沿用。现在有“更换参考作品”按钮。
- 打包后的窗口程序里，错误处理本身会报错，错误对话框弹不出来。
- `--help` / `--version` 会启动界面，而不是打印帮助。
- AI 命令行方式：
  - Windows 下带引号的路径找不到；
  - 超时后 node 子进程不退出；
  - 缩略图不删除；
  - AI 回复按 HTML 渲染。
- 框选层被系统关闭（如 Alt+F4）后，主窗口一直隐藏。
- 快捷键：一个无效时，另一个已被保存。
- 分析尚未结束就关窗口时，后台结果回调报错。

### 本机服务（插件后端）

- **DNS 重绑定**：现在只接受以 127.0.0.1 / localhost 访问。
- **输入校验**：
  - 负数或超大的 Content-Length、尺寸返回 400，不会挂起，也不会耗尽内存；
  - 非法 JSON 返回 400；
  - 内部错误返回 500 并附中文原因（以前直接断开连接，插件只能显示“连不上”）。
- **校准**：
  - 拒绝尺寸不对的色卡；
  - 拒绝空的拟合，不会覆盖已有校准；
  - 加锁，限制样本数量。
- **蒙版**：
  - 可以返回整幅文档大小、分析范围以外为 0 的蒙版，局部图层生成的调整不会作用到范围以外；
  - 放大改用 Pillow，6000×4000 约 0.13 秒（以前约 7 秒，PS 会卡住）。

### PS 插件

- batchPlay 出错不会抛异常。现在逐步检查返回结果和新图层 ID，避免把原图层改名或把蒙版写到原图层上。
- 先取回全部蒙版再建图层；中途失败时不提交历史记录（整体撤回）。
- 图层类型按 PS 自己的 `constants.LayerKind` 取值，避免名字写错漏判。
- ACR 校准在单独的色卡文档里进行，结束后关闭；“合并可见图层”生成 Camera Raw 图层时改用盖印可见图层。
- 打开 Camera Raw 对话框时使用 interactive 模式。

### 打包与文档

- 两种构建方式都安装 Claude API、RAW、AI 抠皮肤的依赖。
- 模型下载遇到 HTTP 错误就失败，并做 SHA-256 校验。
- README 的“已知限制”、测试数量、插件启动方式等与代码不一致的地方已更正。
- README 写明 API Key 以明文保存在本机设置里。

# 第六轮：分析对象（透明图层 / 调整图层）、调整方向与幅度、高光阴影识别、暗调人像

## 分析对象（插件）

新增默认的分析对象「当前图层及以下（看到的画面）」：选中的是调整图层、图层组、透明图层、智能对象都能分析。读像素时临时隐藏选中图层上方的图层、读合成画面，读完立即恢复，这一步的历史记录整体丢弃——不新建盖印图层，文档不留改动。生成的调整图层放在选中图层正上方；生成后直接再分析，就是连同新图层一起复查。原来的「只看当前图层的像素」保留（抠出来的透明人像单独分析时用），「合并可见图层」不变。Camera Raw 图层在这个模式下盖印同一个画面。

## 调整方向与幅度、高光阴影、暗调（核心，17 处修复）

新增系统性的方向测试（155 个场景）：把每个生成的图层按蒙版用独立的 PS 调整模型作用到实际像素上，检查被修正的量朝卡片说的目标移动、不过头，并且方向词（往红 / 往黄 / 往青 / 提亮 / 压深…）与数值符号一致。检验过测试不是空的：把所有图层效果取反后，各类图层都会失败。

| 问题 | 修复 |
|---|---|
| 暗调人像（皮肤 L* 46）在默认“自然通用”下被提亮 +22 L*、说“明度偏低”；白皙皮肤被压暗 | “自然通用”只看色相和浓淡，明度保持；其他风格只在超出该风格的明度区间时拉回区间边缘（「暗调」已经够暗就不动） |
| 暗调画面套用有对比要求的风格（21 个）时高光被提亮 | 暗调画面只压深暗部、不提亮；对比不足不扣匹配分 |
| 日系清新套在暗调图上，中间调一次提亮 18→60 | 每次最多 15 L*，其余提示靠曝光 / 布光 |
| 低饱和的暗调 / 高调画面（没选风格）被判“整体缺色”，加自然饱和度和 S 曲线 | 只给中性说明；选了鲜艳风格（如 Velvia）才建议加饱和 |
| 高调画面靠压暗加对比 | 不压暗，只提示 |
| 过曝的白（255）稀释了高光色调，判成“中性”后反而加暖；仿色白平衡被低估一半 | 裁切像素不参与色调统计 |
| 暗调画面的“高光”其实是中灰；高调画面的“阴影”其实是浅灰 | 高光要求 L* ≥ 60、阴影 ≤ 45 且至少占 1%，否则说明“没有真正的高光 / 阴影” |
| 皮肤上的镜面反光被当成“高光偏洋红 / 发青” | 排除反光和裁切像素，且该段要与中间调明度相差 4 L* 以上 |
| 很暗但带颜色的像素被当成中性黑 | 最暗处的中性判定更严格 |
| 肤色不均匀的图层蒙版覆盖整个外接矩形，把正常皮肤往反方向推（8.5° → −4.1°） | 只覆盖偏色的小块 |
| 偏红橙 / 偏青绿小块的色彩平衡用固定值，深肤色上过头 | 按小块的实际颜色求解 |
| 合并的色相范围不按像素占比加权：占 0.1% 的颜色把肤色拉偏 20° | 按占比加权；占比 < 1% 的通道不给建议 |
| PS 色相/饱和度的“明度”会把颜色冲灰 | 同时补饱和度 |
| 仿色的颜色建议在影调曲线之前算，曲线已经提亮后又给明亮度 +40 | 先按曲线处理后的画面再算颜色 |
| 统一色“往目标靠”忽略了浓淡，模拟后色差反而变大 | 同时调饱和度 |

需要在真实照片上调的阈值：暗调判定（中位明度 ≤ 35 且明度 ≥ 70 的像素 < 10%）、高调判定（中位明度 ≥ 72）；色相/饱和度“明度”的实际效果；小块蒙版的羽化观感。

## 核心算法

| 问题 | 修复 |
|---|---|
| 影调曲线的两个端点永远不动：最暗 / 最亮的分位已经是死黑 / 死白时，“压缩反差”根本做不到，重新分析也不会收敛；只往一端拉时另一段被拉得很陡 | 死黑 / 死白时移动黑场 / 白场端点（同样受 45 级限制） |
| 曲线点只要求相隔 4 级：暗部出现 15 倍的陡坡，PS 的平滑曲线还会在暗部来回打折（明暗翻转） | 点之间至少 12 级，相邻斜率限制在 1/3–3 |
| 曲线按“明度”算，但作用在 R/G/B 各通道：彩色画面调完到不了目标影调 | 按“作用在 RGB 上、图层混合模式为明度”的实际效果模拟并修正几次 |
| 曲线文字和曲线点可能相反（说“整体提亮”，其中一个点在压暗） | 文字直接按曲线点写：“提亮 44→58、91→106；压暗 164→150” |
| 极端直方图（大部分死黑 + 少量死白）生成一条什么都不改的曲线图层，文字是“RGB 曲线（）：。” | 曲线拉不动时不生成图层，提示回 RAW 调曝光 |
| 标题 / 九宫格和影调卡用的采样不同，边界附近会说成两种影调 | 用同一批像素 |
| 选了影调风格后，影调卡把整体程度抬成“明显”、挡掉“未发现明显问题” | 影调卡是“离目标多远”，不计入脏色 / 偏色的程度 |
| 仿色曲线丢掉已经和参考一致的分位，曲线从两边插值过来把它也带着动（中间调被提亮 11 L*） | 一致的分位保留为不动的锚点 |
| 颜色模板的“常用做法”里还有黑场、对比、提亮、S 曲线；黑金的色相/饱和度图层会压暗冷色 | 常用做法里讲明暗的部分去掉（只留通道曲线、饱和度、色温等颜色部分）；颜色模板的图层不再改明度 |
| 肤色风格可以把皮肤一次提亮 +67 级，和影调风格叠加后超过目标 | 皮肤明度一次最多 12 L*，并说明整张图的明暗用影调风格 |
| 脏色 / 区域检查的“发闷”会生成加对比的曲线图层 | 只给文字建议，不替用户改明暗 |
| 暗的、发闷的图（没选影调风格）被建议选「白亮通透」 | 只列和现在同一基调的长调风格，并说明“刻意的柔和就保持不动” |
| 影调已经符合（例如选了胶片、本来就是中短调），缺色卡还说“反差按上面影调卡的曲线调” | 只有影调卡真的有曲线时才这样说 |
| 目标影调决定基调时，颜色卡写“高调画面（中位明度 18）” | 改成“目标影调是高短调：颜色按高调处理” |
| 影调曲线是“正常”混合，提亮 / 压暗时颜色的浓淡也跟着变 | 影调曲线图层的混合模式设为“明度”（插件生成时直接设好） |

# 第十轮：按原图尺寸检查每个像素 / 取点误差

用户反馈：同一张图在插件里和桌面版里结论不一样。原因是两边看的像素不同：插件先把文档缩到长边 2048 再传给服务，桌面版和服务又把超过约 200 万像素的选区降采样。几个像素大的杂色点、细的偏色边，缩小以后会被平均掉，所以图越大、结论越容易不同。

## 一、改为原图尺寸

| 以前 | 现在 |
|---|---|
| 插件读像素时长边缩到 2048 | 按原图尺寸读，不缩小；超过 1 亿像素的文档才缩小，并在结果里说明 |
| 插件“参考图选文件”缩到长边 2048 | 按原图尺寸（同样超过 1 亿像素才缩小，按面积平均） |
| 各分析降采样到约 200 万像素（脏色、肤色、均匀度、整图色彩、统一色、仿色、影调） | 不降采样（上限 1.6 亿像素，正常照片都不会碰到），掩码与原图一一对应 |
| “纯色图层”只抽查 20 万个像素：纯色里零星几个杂色点会被漏掉，整张图被拒绝分析 | 看每一个像素 |
| 选区取色的肤色规则 / 纯度只抽查 5 万个像素 | 每个像素都算 |

**怎么做到不慢**：一张照片几千万个像素，但不同的颜色一般只有十几万到一两百万种。只和颜色有关的判断（Lab、色相、色度、属于哪个通道、是不是对立色、是不是发灰候选）每种颜色只算一次，再按编号查回每个像素；只和颜色有关的统计（占比、平均、中位数、分位数、主色聚类）按“每种颜色 × 它的像素数”加权，结果和逐个像素算完全一样（加权分位数与 `np.percentile` 的线性插值一致，有测试）。和位置有关的判断（边缘、是否孤立、成片还是散点、在哪一块）仍然逐个像素做。

耗时（合成人像，带噪声，单线程）：

| 模式 | 2400 万像素 | 4500 万像素 |
|---|---|---|
| 脏色 / 区域 | 5.1 秒 | 8.8 秒 |
| 整图扫描 | 6.7 秒 | 11.0 秒 |
| 肤色 | 5.8 秒 | 10.4 秒 |
| 整图色彩（含颜色模板、影调） | 5.1 秒 | 5.6 秒 |
| 统一色 | 1.6 秒 | 2.8 秒 |
| 仿色 | 2.6 秒（以前直接按原图算要 60 秒） | 4.0 秒 |

4500 万像素时进程内存峰值约 2.4 GB。

比以前的“缩小后分析”慢（以前 1 秒左右），但同一张图在插件、桌面版、局部框选里看到的是同一批像素，结论一致；单个像素的杂色也能找到。

## 二、取点 / 取色误差

| 问题 | 修复 |
|---|---|
| 插件“读取前景色”用文档 RGB 再换算 Lab：前景色在 PS 里是精确值，换算回 8 位 RGB 再转 Lab 会差一点，非 sRGB 文档差更多 | 直接用 PS 给的前景色 Lab |
| 羽化选区：半选中的边缘像素按全选计入平均色，比 PS 里看到的偏向背景 | 按选中程度加权平均；肤色规则 / 纯度只看选中一半以上的像素 |
| 桌面版点选取点用四舍五入：点在像素右半边会取到右边那一个像素（差 1 像素） | 按鼠标按下处所在的像素（向下取整），和 PS 吸管一致 |
| 靠近图像边缘的 5×5 取样实际只有 9 / 15 个像素，仍显示“5×5” | 显示“5×5（靠边，实际 9 个像素）” |
| 仿色曲线：参考的暗部是死黑 / 亮部是死白时，曲线点落在 0 或 255 上，和端点重复，样条除以 0 | 端点只留一个 |

另外仍然要注意（软件改不了）：桌面版“屏幕取色”取的是屏幕上显示的颜色，PS 缩放小于 100% 或系统缩放不是 100% 时，一个屏幕点对应多个图像像素，已经被 PS 缩小时平均过；要精确请打开原文件或用插件。

# 第十一轮：原图尺寸下提速

用户要求：每个像素都检查，但速度要快。结果不变（逐像素判断和统计的定义都没改），只改算法和执行方式。

| 做法 | 说明 |
|---|---|
| 一次分析只给颜色编号一次 | 以前脏色、统计、阴影 / 高光分段、肤色、均匀度、影调各自把整张图重新编号（2–3 次）；现在同一次分析共用一份 |
| 编号更快 | 三个通道补一个 0 字节当成 32 位整数看（不逐通道移位）；按行分块多线程；用“出现过的颜色”表代替 1600 万格的计数 |
| 只在需要时建逐像素的图 | 有彩色 / 对立色 / 主色族 / 发灰候选按颜色算好，一次查回 1 个字节的类别码；没有对立色、没有发灰候选时不建这些图，也不算边缘 |
| 互不依赖的几项同时算 | 区域：统计 + 脏色；肤色：统计 + 脏色 + 均匀度；扫描：统计 + 脏色；仿色：两张图的颜色、主色聚类同时算 |
| 整图扫描逐块检查多线程，按颜色查小表 | 每块的主色相直方图、色度 × cos / sin 按颜色算好（几十万种颜色的小表），块内只查表求和；平滑用一个矩阵乘法；不再建 4 张整幅的浮点图 |
| 邻居检查 | 孤立像素比例、对立色与主色相邻对数：问题像素很少时只看它们的邻居，多时按行分块多线程 |
| 统一色 | 小块的平均色相只数这一类颜色的像素（按坐标），不建整幅的浮点图 |
| k-means | 距离用矩阵乘法、中心用加权计数，同样的结果快几倍 |
| 区域统计的分位数 | 同一组数的几个分位数只排序一次；RGB 中位数按 256 格直方图求（不排序） |
| 肤色快速规则、肤色调整 | 以前按 2 万个降采样像素算平均和“符合比例”，现在按全部像素（按颜色加权），也更快 |

耗时（4 核测试机，合成人像带噪声，同一进程连续 3 次的中间值；PS 读像素和传给服务的时间不在内）：

| 模式 | 2400 万像素 以前 → 现在 | 4500 万像素 以前 → 现在 |
|---|---|---|
| 脏色 / 区域 | 5.1 → 1.5 秒 | 8.8 → 2.9 秒 |
| 整图扫描 | 6.7 → 2.0–2.5 秒 | 11.0 → 4.1 秒 |
| 肤色 | 5.8 → 2.0–2.4 秒 | 10.4 → 3.7–4.9 秒 |
| 整图色彩 | 5.1 → 1.1 秒 | 5.6 → 1.6–2.2 秒 |
| 统一色 | 1.6 → 0.4 秒 | 2.8 → 0.9–1.3 秒 |
| 仿色 | 2.6 → 1.7–2.0 秒 | 4.0 → 3.5 秒 |

核心数更多的电脑会更快（分块和并行按 CPU 核数，最多 8 线程）。结果和改之前一致：全部 857 个测试通过；新的算法（块内主色相、邻居计数、平滑矩阵、整数分位数）都和旧算法逐一对比过，只有块内主色相在 300 块里有 1 块差 0.05°（float32 的边界像素）。

# 第十二轮：1 亿像素中画幅——先出结果、再精查、复用、快速精度

用户反馈：1 亿像素的中画幅还是慢，要折中办法。做了四件事，前三件不降低精度：

## 1. 只在可疑的地方逐像素做（结果不变）

| 做法 | 说明 |
|---|---|
| 整图扫描逐块检查 | 每块先数各种颜色有几个像素（按颜色编号计数），主色相、对立色有多少都按颜色算；大多数块到这里就知道没有散点，不用逐像素建图。和以前逐像素算完全一样（对比旧版本 16 组结果：字段、掩码、问题位置全部相同） |
| 边缘 | 只在发灰候选像素上算明度梯度（候选少时按坐标取上下左右，多时只算含有候选的行），与对整幅图 np.gradient 再取这些位置逐一相同 |
| 问题位置 | 每一处只在自己的外框里统计；每块计数按列合并，不再列出几千万个坐标 |
| 掩码 | 不再经过 64 位的中间数组（1 亿像素时这一步 2 秒 → 0.15 秒） |

## 2. 先出快速结果，原图精查在后台（桌面版、插件）

- 原图精度下，超过 2000 万像素的图先按约 1200 万像素（按格平均）算一遍，马上显示，标“⏳ 快速结果”；原图精查接着在后台做，完成后替换，并说明结论有没有变化（整体程度、新发现、不再算问题的）。
- 结果对象带 `precision`（full / preview / fast），桌面版报告和插件卡片据此显示说明；问题位置和蒙版按原图坐标换算，快速结果的标记也落在正确位置。
- 插件：分析请求带 `progressive=1`，服务先回快速结果和 `refine` 令牌，插件用 `GET /refined` 等精查结果；期间又分析过就丢弃；已经按快速结果生成了图层就不替换、只提示。服务协议升到 4。
- 精查确实会改变结论（测试图里肤色快速结果“正常”、原图“轻微”），所以快速结果只作为先看的参考。

## 3. 同一张图再分析时复用颜色编号

- 引擎记住最近两张图的颜色编号和缩小图（按数组本身；取用前核对内容指纹，数组被改写过就不用）。换影调风格、颜色模板、肤色风格重算，或快速结果之后的原图精查，都不再重新编号。
- 插件每次都会重新传像素：服务按内容（4 段 CRC32，1 亿像素约 0.1 秒）认出同一张图，用同一份准备好的数组。只差一个像素也认得出不同（有测试）。

## 4. 「快速」分析精度（可选，默认关）

- 桌面版：设置 → 分析精度；插件：分析按钮下的「精度」。超过 2400 万像素的图按格平均缩小后分析（插件直接让 PS 缩小读取，读、传都快），结果标明“快速精度”。

## 耗时（4 核测试机，1 亿像素合成人像带噪声）

| 模式 | 快速结果 | 原图精查（后台） | 同一张图换设置重算 | 「快速」精度 | 以前（原图一步） |
|---|---|---|---|---|---|
| 脏色 / 区域 | 0.9 秒 | 4–5 秒 | 2.3 秒 | 0.8 秒 | 3.8 秒 |
| 整图扫描 | 0.9 秒 | 3–4.5 秒 | 2.1 秒 | 1.2 秒 | 5.6–7.5 秒 |
| 肤色 | 2.3 秒 | 5 秒 | 3.5 秒 | 1.3 秒 | 5.8 秒 |
| 整图色彩 | 0.9 秒 | 2.3–3 秒 | 0.6 秒 | 1.2 秒 | 2.0 秒 |

4500 万像素：快速结果 0.65–0.9 秒，原图精查 1.5–2.7 秒，换设置重算 0.6–1.4 秒。原图精查紧接在快速结果之后时，这台测试机第一次用新内存很慢（首次写入 192 MB 要 0.06–1.7 秒），所以表里精查比单独冷启动略慢；正常电脑上差别小。

未做：PS 读 1 亿像素和传给服务的时间这里测不了（数据约 300–400 MB）；「快速」精度下插件直接缩小读取，可以省掉大部分。

## 补充：快速结果会不会和原图结果冲突、会不会一直在算

- 会不同，以原图精查为准。测试（人像 / 暗调 / 高调 / 天空加散点，区域、整图扫描、肤色三种分析，共 15 组）里 14 组程度和问题完全一致；不同的情形：一两个像素大的杂色点被平均掉（快速结果漏报、分数偏低），分数在两个程度的分界附近差一级，偶尔颜色交界处平均出的中间色被当成发灰（快速结果多报）。颜色分布类结论（影调、主色、丰富度、肤色平均色）基本一致。
- 插件：快速结果出来后，生成图层的按钮等精查完成才可用（图层要按精查结果建）；精查失败时可以按快速结果生成。
- 只在点击时分析，PS 里调色不触发计算。精查还没完成时又分析了一次：插件把上一次的令牌带给服务（supersede），服务让那次精查在下一个检查点停下；桌面版在这条结果被按新设置重算、被替换或被删除时停掉它的精查。分析里每次分块并行前后都检查一次（一次分析几十个检查点），停下通常不到 0.5 秒。

# 第十三轮：去掉快速模式和“先出快速结果”，一律原图、尽量 2 秒内

用户的判断：如果原图分析平均能在 2 秒内，就不需要快速模式；快速结果会让人误解（它和原图结论可能不同）。所以：

- **去掉**：「分析精度」设置（桌面版、插件）、“先出快速结果再精查”、服务的 `precision` / `progressive` / `/refined` / `supersede`（协议升到 5；旧插件发来的这些参数被忽略），结果里的精度标记。
- **保留**：同一张图再分析时复用颜色编号；被新的分析取代时停下（桌面版改设置时上一次还没算完的重算马上停掉）。

继续提速（结果不变：与上一版逐项对比字段、掩码、问题位置，合成测速图和测试图全部相同）：

| 做法 | 说明 |
|---|---|
| 给颜色编号 | 从每个像素起点按小端读 4 个字节、去掉最高字节（不再补字节、逐通道移位），快 4 倍；编号写回同一块内存；每种颜色的像素数在编号时顺便数好 |
| 查表 | `np.take(..., out=)` 默认模式会先写到临时缓冲再拷回，改用 `mode="clip"`（编号一定合法） |
| 计数 | 蒙版全是 True 时直接用总数；同一个蒙版（统计、脏色、肤色、均匀度都要）只数一次，几项同时要时后来的等前面的数完 |
| 发灰像素数 | 用“候选数 − 在边缘上去掉的数”，不再把发灰图整幅数一遍 |
| 阴影 / 高光分段 | 用脏色检查按颜色数好的“正常”像素数，不再扫整幅掩码 |
| 整图扫描 | 掩码按颜色查一次；整幅有效时不另建“有彩色”图；每块的散点按颜色数好，后面不再扫整幅 |
| 边缘 | 明度梯度直接就地算（与 np.gradient 逐位相同），不建 np.gradient 的中间数组 |
| 问题位置的统计 | 按颜色数好再加权（中位数、平均色相），不再对几百万个像素逐个排序 |
| 均匀度 | 各小块分给几个线程；“几乎无彩不算皮肤”按颜色排除，不建整幅图 |
| 其余整幅操作 | 取类别位、按表查掩码、按蒙版写值、列出坐标都按块多线程 |

4 核测试机（这台机器第一次用新内存很慢、同一项多次测相差可到 50%）：

| 合成人像 | 2400 万像素 | 4500 万像素 | 1 亿像素 | 1 亿像素换设置重算 |
|---|---|---|---|---|
| 脏色 / 区域 | 0.4–0.6 秒 | 0.6–0.9 秒 | 2.2–2.6 秒 | 1.3 秒 |
| 整图扫描 | 1.0–1.6 秒 | 1.5–1.8 秒 | 2.6–3.0 秒 | — |
| 人像肤色 | 0.8–1.0 秒 | 0.9–1.1 秒 | 2.0–2.4 秒 | 1.4–1.7 秒 |
| 整图色彩 | 0.6 秒 | 0.7 秒 | 1.1 秒 | 0.5 秒 |

四种平均：2400 万像素约 0.8 秒，4500 万像素约 1.1 秒，1 亿像素约 2.2 秒（换设置重算约 1.2 秒）。新增 `colordoctor bench` 在用户自己的电脑上测。

没做到的：1 亿像素的整图扫描和脏色仍在 2–3 秒（这台 4 核机）；剩下的主要是给颜色编号（约 1 秒，所有分析的共同起点）和噪声多的图里逐像素查明度（颜色种类多到几百万，查表慢）。
